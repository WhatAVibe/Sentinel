# Sentinel v2 encryption (QR key + phone-mediated watch)

Status: implemented from release 3.0.0. Encrypted mode is the default for every new pairing.
`docs/SECURITY.md` records the threat model and what remains plaintext.

## Threat model

Protected: a passive or curious relay operator (the normal case for a shared relay), a stolen relay
backup, and anyone reading `storage/` or SQLite. The relay only sees ciphertext for events, messages and
screenshots, plus routing metadata.

Not protected: an endpoint (PC/phone/watch) that is already compromised, and metadata needed for routing and
alerts (device name, timestamps, category, severity, screenshot size/dimensions/count). Manual URL+code
pairing **cannot** carry a key without exposing it to the relay, so encrypted devices must pair by QR
(phone) or through the phone over Bluetooth (watch). The old manual path stays available only for a
deliberate plaintext device.

## Key

- One 32-byte data key (DEK) per PC, generated by the agent on first pairing and stored DPAPI-protected in
  `config.json` (`ProtectedDataKey`).
- The DEK is put **only** in the pairing QR (field `k`, base64) and in the phone→watch Bluetooth payload.
  It never reaches the relay.
- Devices store the DEK in platform secure storage (phone `flutter_secure_storage`, watch Keystore-encrypted
  prefs, agent DPAPI).
- Revoking a device doesn't rotate the DEK; to rotate, unpair all devices and pair again (the agent generates
  a new key when no devices remain). Unpairing the last device deletes the stored key.

## Envelope

```
enc = base64( nonce[12] || ciphertext || tag[16] )
AES-256-GCM, key = DEK, AAD = "sentinel:v2:<kind>"
kind = event | message | shot
```

- Fresh random 12-byte nonce per payload.
- The relay treats `enc` as an opaque string and never attempts decryption.
- `enc_required` on a device means every new event/message/screenshot must carry `enc`; the relay rejects
  plaintext writes with `400 enc_required`.

## Payloads

| Record | Ciphertext plaintext | Plaintext metadata kept |
|---|---|---|
| Event | JSON `{title, detail}` | `ts`, `category`, `severity` |
| Message | JSON `{title, body, reply}` | `direction`, `kind`, `status`, `allow_reply`, timestamps |
| Screenshot | PNG bytes | `ts`, `monitor`, `monitor_name`, `width`, `height`, `trigger`, `size` |

Relay-generated alerts (offline, low disk, low battery, boot) remain plaintext system events: they carry no
user content. Encrypted clients render both.

## Pairing (phone by QR)

1. PC creates a pair request. The agent generates/loads the DEK and includes `enc_required: true` in
   `POST /pair/request`. The QR is `{"v":2,"u":url,"r":request_id,"c":pair_code,"n":name,"k":base64(DEK)}`.
2. The phone scans the QR, keeps `k` locally, and calls `POST /pair/approve` as today. The relay marks the
   device `enc_required`.
3. `pair/approve` returns `enc_required`; the phone stores the DEK in the session.
4. The PC confirms the device with the 6-digit code as today. The DEK never transits the relay.

A manual URL+code pairing on an `enc_required` device is rejected by the phone ("scan the QR to receive the
key") and, if forced, by the relay when it writes plaintext.

## Pairing the watch through the phone

The watch has no camera and its keyboard is painful, so the phone adds the watch:

1. Phone → relay: `POST /api/v1/devices/<did>/companions` with the phone token, `{name, kind: "watch"}`.
   The relay creates a **confirmed** mobile row of kind `watch` and returns `mobile_token`, `mobile_id`.
2. Phone → watch over the Wear OS Data Layer (message path `/sentinel/pair`):
   `{url, device_id, device_name, token, secret, data_key, name}`.
3. Watch stores the session and DEK, then shows the home screen. No code is typed on the watch.
4. The phone lists the watch in Linked devices and can revoke it. The PC does not need to confirm this
   companion because the phone is already an authorised device.

The Flipper keeps using the phone bridge; it never stores the DEK.

## Relay API

- `POST /pair/request` accepts `enc_required` (bool).
- `POST /pair/approve` returns `enc_required`.
- `POST /agent/events`, `POST /agent/messages/<id>/reply`, `POST /agent/screenshots` accept `enc` (and form
  field `enc=1` for screenshots); plaintext fields are cleared when `enc` is present.
- `POST /devices/<id>/message` accepts `enc`; the phone also stores nothing plaintext on the relay.
- `POST /devices/<id>/companions` creates a watch token (mobile auth, same device only, rate limited).
- `GET /devices/<id>/...` serializers include `enc` per row and `enc_required` per device.
- Screenshot files are stored as `<id>.enc`; `GET .../file` returns the ciphertext bytes with
  `Content-Type: application/octet-stream`.

## Client rules

- Agent: encrypt before upload; decrypt incoming message commands before display; local dashboard unchanged.
- Phone: decrypt events/messages/screenshots before rendering; encrypt outgoing messages; never log the DEK
  or plaintext from encrypted rows.
- Watch: stores the DEK from the companion payload; watches don't render events/screenshots, so it is kept
  for future features and to avoid a second pairing protocol.
- Relay: opaque storage, quota enforcement on ciphertext size, no key handling.

## Migration

`3.0.0` is a breaking release. Purge existing devices, phones, events, messages and screenshots, then pair
the PC, phone and watch again. There is intentionally no legacy plaintext fallback for new devices; the
relay rejects mixed writes on `enc_required` devices.
